# 002-cache-pitfalls

## 何を測るか

**AOT キャッシュが効かなくなる 2 つの経路を、出力と起動時間の両方で観測する。**

| 経路 | 何が起きるか |
|---|---|
| キャッシュを作った jar と違う jar に当てる | 既定の出力に warning 1 行 + error 3 行。**キャッシュなしより遅くなる** |
| `-Pnative` の後に `clean` を挟まずビルドし直す | Spring AOT の生成クラスが素の jar に混ざる |

## なぜ測るか

`002-startup-3ways` の `expected.md` が、この 2 件を**生ログの裏づけなしに**書いていたためです。
機械照合用の json ブロックにも入っておらず、`tools/check-provenance.py` は 1 度も見ていませんでした。

🔴 **測り直した結果、1 件目の記述は事実と食い違っていました。**

| 旧記述 | 実測 |
|---|---|
| 食い違うキャッシュは `Opened AOT cache` と表示されたまま**静かに**効かなくなる | **静かではない**。既定の出力に warning 1 行 + error 3 行が出る |
| `Opened AOT cache` と表示される | 既定では **0 行**。`-Xlog:aot` を付けたときだけ 1 行出る（しかも検証の**前**） |
| 基準より 5.4% 遅い（素 0.911s / 食い違い 0.960s） | 同じ土俵（展開した形）で測ると **キャッシュなし 0.783s に対し 0.842s = +7.5%** |

**本当に無言なのは展開を飛ばした場合**です。既定の出力に aot 関連の行が **0 行**しか出ません
（効いていないのではなく半分しか効いていないため、警告の出しようがありません）。

## 測定設計（意図的な選択）

1. **3 アームとも「展開した形」でそろえる。**実行可能 jar のままと展開後では起動時間そのものが違うため、
   土俵をそろえないと「食い違いのせいで遅い」のか「展開していないから速い / 遅い」のかが分離できない。
2. **ラウンドロビン + 捨て走り 1 セット。**`002-startup-3ways` と同じ規律。
3. **jar B は `/hello` の戻り値を 1 行変えて作り直す。**読者が実際にやること（コードを直して
   `mvn package` を打ち直す）を再現する。人工的にバイトを書き換えたりしない。
4. **リポジトリの working tree を書き換えない。**モジュールを一時ディレクトリへ複製してから変更する。
5. **作業ディレクトリは `/tmp` 直下に取る。**既定の `TMPDIR` はユーザー名を含む場所を指すことがあり、
   その絶対パスが JVM の警告行に載って `run.log` へ残る。

## 実行

```bash
bash scenarios/002-cache-pitfalls/run.sh            # 既定 5 セット
bash scenarios/002-cache-pitfalls/run.sh --sets 3   # セット数を変える
bash scenarios/002-cache-pitfalls/run.sh --out /tmp/x
```

## 前提

| 項目 | 要件 |
|---|---|
| モード | **M1**（JDK + Maven） |
| Java | **25 以上**（`-XX:AOTCacheOutput` は JDK 25 の JEP 514） |
| GraalVM | **不要**（`-Pnative` は `spring-boot:process-aot` を走らせるだけで `native-image` を呼ばない） |
| Docker | 不要 |

## 出力

| ファイル | 内容 |
|---|---|
| `results/002-cache-pitfalls/run.log` | 生ログ（既定出力に出た warning / error の実文言を含む） |
| `results/002-cache-pitfalls/summary.json` | 実効値（機械が読む） |
| `scenarios/002-cache-pitfalls/expected.md` | **記事に載せる値の正本**（機械照合する） |

## 測っていないもの

- **展開を飛ばした場合の起動時間**（`002-startup-3ways` の `aotfat` アームが担当）
- 依存の多い実アプリでの差
- 出力を捨てている環境（`> /dev/null` / ログ収集の設定）で警告に気づけるかどうか
- JVM のフラグが作成時と実行時で食い違う場合（未検証）
