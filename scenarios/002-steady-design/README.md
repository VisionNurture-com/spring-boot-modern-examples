# 002-steady-design

## 何を測るか

**`002-steady-throughput` の測定条件が妥当かどうかを、素の JVM だけで振って確かめる。**

| スイープ | 振るもの | 固定するもの | 答える問い |
|---|---|---|---|
| A | 同時実行 16 / 32 / 64 / 128 | n=2,000 | どこで飽和するか |
| B | 計算量 n=2,000 〜 1,000,000 | 同時実行 8 | どこから計算が律速になるか |
| C | ウォームアップ 2 / 8 / 20 / 40 秒 | n=1,000,000・同時実行 8 | 8 秒で頭打ちに達しているか |

## なぜ測るか

`002-steady-throughput` の `expected.md` が、この 3 つを**生ログの裏づけなしに**載せていたためです。
機械照合用の json ブロックにも入っておらず、`tools/check-provenance.py` は 1 度も見ていませんでした。

取り直した値は旧記述とよく一致したため、観測そのものは実際に行われていたと考えられます。
問題は**再現できる形で残っていなかった**ことです。

## 測定設計（意図的な選択）

1. **素の JVM だけで測る。**方式間の比較は `002-steady-throughput` の担当で、ここは条件の妥当性だけを見ます。
2. **A と B はサーバを 1 度だけ立てる。**振っているのはクライアント側の条件なので、サーバの状態はそろえます。
3. 🔴 **C は各点でサーバを立て直す。**同一プロセスで連続実行するとウォームアップが累積し、
   短い側の点が直前の実行のぶんまで温まってしまいます。独立した比較にするため毎回立て直します。
4. **エラー件数も記録する。**飽和の判定でスループットだけを見ると、失敗したぶん速く見える状態を見逃します。

## 実行

```bash
bash scenarios/002-steady-design/run.sh                    # 既定（計測 10 秒 × 13 点）
bash scenarios/002-steady-design/run.sh --duration-sec 5   # 短く回す
bash scenarios/002-steady-design/run.sh --out /tmp/x
```

## 前提

|---|---|

| Java | 25 以上 |
| GraalVM | **不要** |
| Docker | 不要 |

## 出力

| ファイル | 内容 |
|---|---|
| `results/002-steady-design/run.log` | 生ログ（13 点それぞれの rps / p99 / エラー件数） |
| `results/002-steady-design/summary.json` | 実効値（機械が読む） |
| `scenarios/002-steady-design/expected.md` | **記事に載せる値の正本**（機械照合する） |

## 測っていないもの

- **方式間の比較**（`002-steady-throughput` の担当）
- p99 が伸びる内訳（キューイングかコンテキストスイッチか）
- JIT がどの時点で最適化を終えたか（JIT ログは見ていない）
- この機体以外での飽和点
