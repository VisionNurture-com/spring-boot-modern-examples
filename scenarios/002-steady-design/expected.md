# expected: 002-steady-design

> 🔴 **記事に載せる値は本書からしか引きません。**本書の値は `results/002-steady-design/summary.json` と
> `tools/check-provenance.py` で機械照合されます。食い違えば CI（M0）が落ちます。

## なぜこのシナリオを足したか

`002-steady-throughput` の `expected.md` は、測定条件の根拠として次の 3 表を載せていました。

1. 計算量の感度測定（n=20,000 で 43,962 rps ほか）
2. 飽和の確認（同時実行 16 → 128 でスループット横ばい・p99 だけ 0.67 → 7.55 ms）
3. ウォームアップの妥当性（2 秒 3,980.9 → 40 秒 4,032.8 rps）

**どの値も `results/` の `run.log` に 1 件も出現せず**、機械照合用の json ブロックにも入っていませんでした。
本計測の前に手元で振った探索的な実行の値が、ログを残さないまま手書きされたものです。
本シナリオで 3 つとも取り直します。

> ⚠️ **取り直した値は旧記述とよく一致しました。**観測そのものは実際に行われていたと考えられますが、
> **再現できる形で残っていなかった**点が問題です。

## A. 同時実行スイープ（n=2,000 固定・ウォームアップ 8 秒）

サーバは 1 度だけ立て、同時実行だけを変えました。

| 同時実行 | スループット | p99 | エラー |
|---:|---:|---:|---:|
| 16 | **46,279.3 rps** | **0.65 ms** | 0 |
| 32 | 44,593.1 rps | 1.67 ms | 0 |
| 64 | 42,860.9 rps | 3.82 ms | 0 |
| 128 | **42,160.3 rps** | **7.63 ms** | 0 |

**同時実行を 8 倍にしてもスループットは 8.9% しか動かず、p99 だけが 11.7 倍**に伸びました。
待たせているだけで処理量は増えていない状態で、**飽和の兆候**です。
`002-steady-throughput` が同時実行を **8** に固定しているのは、この手前で測るためです。

## B. 計算量スイープ（同時実行 8 固定・ウォームアップ 8 秒）

サーバは 1 度だけ立て、`n` だけを変えました。

| n | スループット | p99 | 支配しているもの |
|---:|---:|---:|---|
| 2,000 | **46,191.7 rps** | 0.27 ms | HTTP の往復 |
| 20,000 | **43,717.6 rps** | 0.27 ms | HTTP の往復 |
| 100,000 | 24,754.6 rps | 0.41 ms | 遷移域 |
| 300,000 | 11,441.4 rps | 0.79 ms | アプリの計算 |
| 1,000,000 | **4,026.2 rps** | 2.13 ms | アプリの計算（ほぼ線形） |

🔴 **計算量を 10 倍（2,000 → 20,000）にしてもスループットは 5.4% しか落ちません。**
この領域ではアプリの計算ではなく HTTP の往復が支配的で、**JIT と AOT の差は現れようがありません**。
`002-steady-throughput` が負荷を 2 種類かけるのは、支配要因の違う 2 点を別々に見るためです。

## C. ウォームアップスイープ（n=1,000,000・同時実行 8）

🔴 **各点でサーバを立て直しています。**同一プロセスで連続実行するとウォームアップが累積し、
短い側の点が直前の実行のぶんまで温まってしまうためです。

| ウォームアップ | スループット | p99 | エラー |
|---:|---:|---:|---:|
| 2 秒 | 4,001.2 rps | 2.35 ms | 0 |
| **8 秒（本計測の値）** | **4,011.1 rps** | 2.19 ms | 0 |
| 20 秒 | 4,029.9 rps | 2.15 ms | 0 |
| 40 秒 | 4,029.9 rps | 2.13 ms | 0 |

**8 秒から 40 秒へ 5 倍に伸ばしても +0.47%** で、20 秒と 40 秒は同じ値でした。
残差は `002-steady-throughput` で Native Image が遅かった幅（軽 5.5% / 重 2.9%）より小さく、
しかも **JVM 側を有利にする方向**のため、ウォームアップを伸ばしても結論は覆りません。

## 記事が主張してよい範囲 / よくない範囲

| 主張 | 可否 |
|---|---|
| 同時実行を 16 から 128 へ振ると、スループットは 8.9% しか動かず p99 が 11.7 倍になった | ✅ |
| 計算量を 2,000 から 20,000 へ 10 倍にしても、スループットは 5.4% しか落ちなかった | ✅ |
| ウォームアップを 8 秒から 40 秒へ伸ばしても +0.47% で頭打ちだった | ✅ |
| したがって同時実行 8・負荷 2 種・ウォームアップ 8 秒という条件は妥当である | ✅ |
| **この機体以外でも同じ点で飽和する** | ❌ 測っていません。CPU コア数とネットワークの構成で変わります |
| **8 秒あればどんなアプリでもウォームアップが終わる** | ❌ 依存の少ない計測用アプリでの結果です |
| **JIT がどの時点で最適化を終えたか** | ❌ 機序は測っていません（JIT ログもコンパイル状況も見ていません） |
| **p99 が伸びた原因はキューイングである** | ❌ 内訳は測っていません。観測したのは p99 の値だけです |
